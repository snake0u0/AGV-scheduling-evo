# 보고서 - evaluator 구현 및 replay 검증 결과

작성 2026-07-23. 선행 문서: `2026-07-23-skeleton-evaluator-design.md`(설계).
원칙: **데이터 변형 금지.** 인스턴스/해/이동시간 값은 파일에 적힌 그대로만 사용했다.

## 결론 (한눈에)

- **타이밍 코어를 구현했고, 문헌의 워크드 예제로 정확히 검증했다.** Berterottière et al. (2024)의
  Table 2-3 / Figure 5-6 예제(2 job, 3 기계, 2 차량)를 넣으면 **Cmax 13이 논문과 일치**하고,
  중간 시각(각 공정의 도착/시작/종료)까지 전부 일치한다. 즉 **시간 계산 로직은 검증되었다.**
- **하지만 54개 공개 해 파일 replay는 0/54 불일치**다. 원인은 우리 코드가 아니라 **공개 해 파일 자체의
  내부 모순**이다: 파일에 적힌 M/V 시퀀스가 요구하는 이동시간이 파일 헤더의 Cmax보다 크다.
  이건 시뮬레이터와 무관한 산술이다(§3).
- **부수 성과 - 규약 2개를 1차 출처로 확정**: "같은 기계로 이어지면 운반 없음"이 2024 논문 원문에
  명시돼 있음을 확인(어제 데이터로 역추론한 것이 원문과 일치). 이동시간 행렬도 논문 Appendix A와
  **바이트 단위로 동일**함을 확인해, 우리 해석(LU=0, 행=출발)이 옳음을 확정.
- **영향**: replay를 "게이트"로 삼으려던 계획은 이 데이터셋에서는 불가능하다. 다만 **evaluator 검증
  자체는 워크드 예제로 달성**했으므로, 다음 단계(GA/LLM)로 진행하는 데 지장은 없다(§5).

## 1. 구현한 것

```
fjspt/
  instance.py            # Instance 모델 + 파서 3종(A/B/C) + 데이터셋 레지스트리
  solution.py            # Solution 모델 + 공개 해 파일 파서
  timing.py              # 타이밍 코어 (유일한 시간 계산 지점) + 구조 정합성 검사
  replay.py              # 공개 해 replay 검증        (python -m fjspt.replay)
  test_paper_example.py  # 논문 워크드 예제 정답 테스트 (python -m fjspt.test_paper_example)
```

설계대로 **"타이밍 코어 1개 + 프론트엔드 2개"** 구조다. A안 자산(`sim/`, `ahd/`)은 건드리지 않았다.

파서 3종 모두 동작 확인:
- **A**(DeroussiNorre, 대체기계가 처리시간을 공유), **B**(표준 FJS), **C**(Fattahi, job 경계를 선행관계
  체인으로 복원. `nJob = 총공정수 - 선행쌍수` 확인: sfjs01 = 4 - 2 = 2 job).
- 헤더 3번째 필드는 읽되 사용하지 않는다(설계 §1d의 이유 그대로).
- 포맷 C는 기계가 0-index라 1..m으로 옮겼다. **값은 그대로**, 인덱스만 정렬한 것이다.

## 2. 타이밍 코어 검증 (통과)

2024 논문의 워크드 예제를 그대로 코드로 옮겨 넣었다(`fjspt/test_paper_example.py`).

| 공정 | 기계 | 도착 | 시작 | 종료 |
|---|---|---|---|---|
| 1 | M2 | 4 | 4 | 5 |
| 2 | M3 | 7 | 7 | 10 |
| 3 | M1 | 2 | 2 | 6 |
| 4 | M3 | 8 | 10 | 13 |

**Cmax = 13**, 논문 Figure 6의 간트 차트와 일치. 공차 이동(V1: M2->M1 3단위, V2: M1->M2 2단위),
차량 대기(V2가 op1 종료를 기다림), 기계 경합(op4가 M3에서 op2를 기다려 8이 아니라 10에 시작)이
모두 논문 그림과 같은 값으로 재현된다.

이로써 다음이 검증됐다: 적재/공차 이동 구분, `pickup = max(차량가용 + 공차, 작업물준비)` 형태,
기계 선후 제약, LU 출발, 복귀 없음.

## 3. Replay 0/54 - 원인은 공개 해 파일

Dauzere 계보 18인스턴스 x {2,4,6}대 = 54케이스 전부 우리 값이 공개 Cmax보다 **크다**.
(예: 01a 2veh 4623 vs 2752, 03a 6veh 2453 vs 2261)

원인을 단계적으로 분리했다.

### 3.1 우리 해석이 틀린 게 아니다

- 레포의 `BerterottiereTravelTimes/layout{5,8,10}.txt`가 2024 논문 **Appendix A의 Table A.12/13/14와
  완전히 동일**함을 확인했다. 표의 행/열 머리글이 `LU, M1..Mm`이므로 **인덱스 0 = LU, 행 = 출발**이라는
  우리 해석이 원문으로 확정된다.
- 그럼에도 혹시 몰라 4가지 해석(원점 위치 x 전치 여부)을 전수 시도했다. **네 가지 모두 동일하게 실패**한다.

### 3.2 차량 경합 문제도 아니다

각 운반에 전용 차량을 하나씩 주어 **차량 경합을 완전히 제거**해도 여전히 공개값을 초과한다
(03a 6veh: 기계부하 하한 2243 -> 경합 없음 2377 -> 공개값 2261). 즉 차량 순서 문제가 아니다.

### 3.3 결정적 근거 - 시뮬레이터 없이도 성립하는 모순

공개 해 파일의 `V` 줄은 각 차량이 맡은 운반 목록을 준다. 그 운반들의 **적재 이동시간 합**은
순서와 무관하게 정해지며, 한 차량이 그만큼은 반드시 움직여야 한다:

| 케이스 | 공개 Cmax | 가장 바쁜 차량의 적재이동 합(공차 제외) |
|---|---|---|
| 07a 2veh | 2686 | **3556** |
| 13a 2veh | 3170 | **5810** |
| 18a 2veh | 2312 | **3779** |

**차량 한 대가 적재 이동만으로 Cmax를 초과한다.** 이건 어떤 시뮬레이터를 쓰든, 순서를 어떻게 잡든
성립하지 않는다. 공차 이동까지 포함하면 격차는 더 커진다(01a 2veh: 가장 바쁜 차량 3488 vs Cmax 2752).

더 일반적으로: 시퀀스가 고정되면 우리 코어가 내는 값은 **그 시퀀스로 가능한 최소 makespan**(모든 작업을
가능한 한 일찍 시작시키므로)이다. 그 최소값이 54케이스 전부에서 헤더의 Cmax보다 크다.
따라서 **파일 안의 M/V 시퀀스와 헤더의 Cmax는 같은 해를 가리키지 않는다**고 결론내릴 수밖에 없다.

### 3.4 방증

2024 논문 Table 8의 Cmax(예: 1a 2veh = 3029, 7a 2veh = 4157, 13a 2veh = 6332)는 레포 파일 헤더
(2752 / 2686 / 3170)와도 다르다. 즉 레포 해 파일은 논문 표와도 어긋난다.
참고로 우리 replay 값(4623 / 6043 / 8531)은 논문 표 쪽에 더 가깝지만 그것과도 일치하지는 않는다.

## 4. DeroussiNorre(fjsp1 -> 134) 도 아직 막혀 있다

이동시간 행렬이 레포에 없다는 건 이미 알고 있었고(설계 §10 R1), 후보 가설
"Bilge-Ulusoy Layout 1(4기계)을 기계 2배 복제"를 8가지 변형(원점 위치 2 x 전치 2 x 쌍 내부 거리 2)으로
전수 시도했다. **전부 불일치**(fjsp1 기준 160~166 vs 공개 134).

2024 논문 §7.1은 data set 1이 "Deroussi & Norre (2010)이 Bilge & Ulusoy (1995)를 8기계·유연도 2로 확장한
것"이라고만 하고 레이아웃은 싣지 않았다(Appendix A는 data set 5 전용). **따라서 Deroussi & Norre (2010)
원문 확보가 필요**하다. STATUS.md의 "채워야 할 원전" 목록에 이미 있다.

## 5. 그래서 다음에 뭘 하나

**replay를 게이트로 삼으려던 계획은 수정한다.** 이유는 우리가 못 만들어서가 아니라 데이터가 그렇기 때문이다.

- **evaluator 검증은 이미 달성됐다**: 문헌의 워크드 예제를 중간 시각까지 정확히 재현한다.
  논문에 "우리 evaluator는 원 논문의 예제를 정확히 재현한다"고 쓰고 표를 넣을 수 있다.
  replay만큼 강하진 않지만, 1차 출처 기반의 유효한 검증이다.
- **성능 비교는 그대로 가능하다.** 우리가 필요한 건 상대의 *해 파일*이 아니라 상대의 *보고된 Cmax*다.
  같은 인스턴스 + 같은 Appendix A 이동시간 행렬 위에서 우리 GA/LLM의 Cmax를 논문 Table 8의 Cmax와
  비교하면 된다. 이게 원래 문헌들이 서로 비교하는 방식이다.
- **다만 비교 기준을 명확히 해야 한다.** 레포 해 파일 헤더의 Cmax는 **인용하지 않는다**(§3에서 내부
  모순을 확인했으므로). 인용은 **2024 논문 Table 8**(그리고 data set 1은 Table 4)의 값으로 한다.

### 착수 순서(수정)

```
1. [완료] 파서 3종 + 타이밍 코어 + 워크드 예제 검증
2. decode(OS, MS, rule) 구현
   -> 검증: decode 결과를 simulate에 재투입해 Cmax 동일(자기검증)
3. rules.py(Decoding1/2) + ga.py
   -> 검증: Dauzere 인스턴스에서 2024 논문 Table 8 값과 같은 자릿수인지
4. LLM 루프 연결
```

### 남은 조치

| 항목 | 조치 |
|---|---|
| Deroussi & Norre (2010) 원문 | 확보 -> data set 1 레이아웃 -> fjsp1 replay 재시도 |
| 레포 해 파일 모순 | 저자에게 문의 가치 있음. 우리 쪽 발견이 맞다면 데이터 이슈 리포트 자체가 기여 |
| 인용 기준 | 논문 표의 Cmax만 인용. 레포 헤더 Cmax 사용 금지 |
| `setb4xxx.txt` | 기존대로 사용 금지(레지스트리에 `BLOCKED`로 명시함) |
