# 보고서 - GitHub 재사용 코드로 인스턴스-투-Cmax 파이프라인 실측 검증

작성 2026-07-23.

## 결론 (한눈에)

- `Aihong-Sun/GA-heuristic-approach_to_simultaneous_-scheduling_or_AGV_and_machine` 저장소의
  `GA_VAA.py`(AGV 배차 디코더 `VAA_decode` + GA)를 가져와 실제 인스턴스(Kumar 2011, Problem 1.1,
  5job x 4machine x 2AGV)로 입력부터 Cmax 계산까지 전 과정을 돌려봤다.
- 처음 실행 결과는 Cmax=130으로, 문헌 5개 독립 방법(STW/UGA/AGA/RGA/PDE, 전부 96으로 일치)보다 35% 나빴다.
  원인을 추적한 결과 디코더 로직 자체가 아니라 **저장소 자체의 데이터/청크 구성 버그**였고, 한 줄짜리
  데이터 정리(순수 trim, 스케줄링 로직 무수정)만으로 랜덤 서치조차 정확히 96을 재현했다.
- 즉 `VAA_decode`(AGV 그리디 배차: 유휴 AGV 중 완료시각 최소가 되는 AGV 선택 + deadhead/loaded travel 계산)는
  **문헌값과 정확히 일치하는, 검증된 재사용 가능 코드**임을 확인했다. 외부 리뷰어 검증 관점에서 우리가
  직접 짠 디코더보다 신뢰도가 높다.
- 단, 이 코드는 AGV 선택만 처리하고 기계 경로는 고정(단일 경로)으로 가정한다. 우리 실제 목표 인스턴스
  (DeroussiNorre 등, 공정마다 대안 기계 2개+)의 "기계 선택" 로직은 이 저장소에 없다 - 이는 문제가 아니라
  오히려 우리 프로젝트가 LLM으로 evolve하려는 대상 그 자체다.

## 과정

### 1. 저장소 재확인 - 실행 가능한 파이프라인이 통째로 있는가?

`Test1.py`/`Test2.py`는 인스턴스 파일을 읽는 스크립트가 아니라 무작위 테스트 데이터를 생성하는 스크립트였고,
`intsance_transfer.py`는 저자가 자기 로컬 파일(`C:/Users/Administrator/...`)을 pkl로 변환했던 일회성 스크립트였다.
`Text_extract.py`(저자가 pkl -> GA 입력 형태로 바꾸는 실제 로더)를 찾아서 읽고 나서야 정확한 데이터 흐름을 파악했다:

```python
n, m, agv_num = len(d[3]), d[1], d[2]
PT, agv_trans, MT = d[3], d[5], d[4]
MT = [[k-1 for k in mi] for mi in MT]   # 1-indexed -> 0-indexed
```

즉 "인스턴스 파일 -> 돌리기"까지 완성된 실행 스크립트는 저장소에 없고, 이 로더 로직을 참고해 우리가 직접
글루 코드를 짜야 한다는 점은 예상대로 확인됐다(앞선 §2 조사 - `docs/reports/2026-07-12-...` - 에서 이미
"로더 스크립트 부재"로 데이터 출처로는 배제했던 것과 일치).

### 2. E11.pkl(Kumar 2011 Problem 1.1)로 1차 실행

`E11.pkl`을 언피클해서 나온 값(PT/MT/travel matrix)이 Kumar et al. (2011) 논문 부록 Table 4 "Job Set 1" +
Fig. 3 "Layout 1"과 정확히 일치함을 Zotero 원문 대조로 확인했다(`agv-llm-heuristic` 컬렉션, key `KQK9HJMJ`).
저장소의 `Text_extract.data()` 로직 그대로 GA에 연결해 `GA(n,m,agv_num,PT,MT,agv_trans,pop_size=100,gene_size=100)`를
돌린 결과:

```
Best Cmax: 130   (elapsed 0.26s)
```

Kumar 2011 Table 5는 같은 인스턴스에 대해 STW=96, UGA=96, AGA=96, RGA=96, Kumar 자신의 PDE-1/PDE-2=96/96으로
5개 독립 방법이 전부 일치한다. 130은 이보다 35% 나쁨 - 재사용한 코드를 그대로 믿으면 안 된다는 신호.

### 3. 원인 진단 - 디코더 버그인가, 데이터/GA 버그인가?

디코더 로직만 떼어 랜덤 순열 5만 개를 직접 시도(`GA` 없이 `RJSP.VAA_decode`만 호출)했더니 최선이 124 -
여전히 96에 못 미쳤다. PT/MT를 다시 보니 각 job의 마지막 원소가 `PT=0, MT=depot`인 항목이었다:
원본 pkl 데이터가 "완료 후 depot로 복귀"를 duration=0짜리 가짜 공정으로 인코딩해 놓았는데, 저장소의
청크 구성 코드(`len(Pi)`로 공정 수를 셈)가 이 가짜 공정까지 실제 공정처럼 청크에 포함시켜, job마다
불필요한 AGV 왕복(depot 복귀 이동시간)이 Cmax에 그대로 더해지고 있었다.

이 마지막 원소를 순수하게 잘라내고(스케줄링/디코드 로직은 한 글자도 안 건드림) 같은 5만 개 랜덤 순열
서치를 다시 돌리니:

```
best Cmax over 50000 random permutations (trimmed): 96
```

정확히 문헌값과 일치. 저장소의 GA(크로스오버 버그 있는 상태 그대로, 아래 참고)로도 5회 반복 실행:

```
96, 96, 97, 97, 98, 100
```

96(최적)을 재현하거나 근접함을 확인.

부수적으로 발견한 두 번째 버그: `GA.POX()`(크로스오버 함수)가 `new_CHS1`/`new_CHS2`를 계산해 놓고
정작 `return CHS1, CHS2`(원본 미변경 값)를 반환한다 - 죽은 코드. 즉 이 "GA"는 실질적으로
mutation-only 랜덤 로컬서치였다. 그럼에도 5job 규모에서는 96 근처에 잘 도달했다.

## 결론이 우리 프로젝트에 갖는 의미

- `VAA_decode`(그리디 AGV 배차: 유휴 AGV별 완료시각 계산 -> 최소값 선택)는 **검증된, 재사용 가능한
  3rd-party 코드**다. AGV 선택/시퀀싱 파트의 "정답 기준선" 혹은 LLM-AHD의 seed 휴리스틱 후보로 쓸 수 있다.
- 이 코드는 기계 경로가 고정된 인스턴스(대안 기계 없음)에서만 검증됐다. 우리 실제 목표(DeroussiNorre 등
  진짜 FJSP, 공정당 대안 기계 2개+)에 쓰려면 기계 선택 로직을 별도로 얹어야 하는데, 이건 우리가 만들
  "코드가 없어서" 채우는 구멍이 아니라 프로젝트의 평가/진화 대상 그 자체(두 계층 인코딩의 MS 레이어)다.
- 재사용 시 반드시 지킬 것: 저장소의 pkl 데이터를 그대로 쓰지 말고, 우리가 직접 파싱하는
  DeroussiNorre/Homayouni_Brandimarte 텍스트 포맷에서는 애초에 이런 가짜 depot-복귀 공정이 없으므로
  (이번 버그는 이 저장소 고유의 pkl 인코딩 방식 문제) 이 특정 trim 로직 자체는 우리 파서에 옮길 필요 없음 -
  다만 "공급된 데이터를 그대로 믿지 말고 항상 원문헌 대조로 검증한다"는 절차 자체는 계속 적용.

## 4. 실제 목표 스케일(Berterottiere/Dauzere, 2AGV) 재테스트

`DeroussiNorre/fjsp1.txt`(문헌 Cmax=134, AGV 2대)로 이어서 테스트하려 했으나, 이 계보는 이동시간 행렬이
없다(§ `_OUR_NOTES.md` (b) 항목에 이미 기록된 gap). 대신 이동시간 행렬이 준비된 Dauzere/Berterottière
계보(`Dauzere_Data/Text/01a.txt` 10job x 5machine + `BerterottiereTravelTimes/layout5.txt` 6x6 이동시간
+ `Berterottiere/dpp2veh/dpp01a_2veh.txt`의 선언된 Cmax=2752, AGV 2대)로 전환해 같은 방식으로 테스트했다.

이번엔 표준 FJS 포맷이라 Kumar 데이터처럼 phantom depot-복귀 공정 문제는 없었지만, 진짜 대안 기계
선택이 필요한 인스턴스라(공정마다 여러 후보 기계 중 하나를 골라야 함) `VAA_decode`가 요구하는
"공정당 고정 (기계,시간) 1개" 형태로 바꾸는 규칙이 우리 쪽에서 하나 필요했다. 가장 단순한 baseline
(SPT: 후보 기계 중 처리시간이 최소인 것 선택)을 적용해 같은 파이프라인(파서 -> SPT 기계선택 ->
재사용 `VAA_decode`/`GA`)을 그대로 돌렸다.

```
n=10 jobs, m=5 machines, agv_num=2, 공정 수(job별)=[15,20,23,18,21,15,17,25,23,19] (총 196공정)
Best Cmax (SPT + 재사용 GA, pop=100, gen=100): 5022
문헌 Cmax(Berterottiere 2024, dpp01a, 2AGV): 2752
elapsed: 4.07s
```

82% 격차로, E11 때보다 훨씬 크다. 이번엔 E11처럼 단일 버그로 설명되는 게 아니라 두 가지가 겹친 것으로
보인다: (1) SPT는 우리가 급조한 가장 단순한 기계선택 규칙일 뿐 문헌의 tabu search가 실제로 쓰는 전략이
아니고, (2) 앞서 확인한 크로스오버 죽은 코드(mutation-only 랜덤서치) 버그가 공정 13개 규모(E11)에서는
100세대 안에 거의 최적에 도달할 만큼 봐줄 만했지만, 공정 196개 규모에서는 탐색 공간이 압도적으로 커져
같은 세대 수로는 어림도 없다. 실제로 이 프로젝트가 풀려는 문제(스마트한 기계+AGV 선택 규칙을 LLM으로
진화)의 필요성을 거꾸로 보여주는 결과이기도 하다 - 단순 규칙 + 약한 탐색으로는 실제 스케일에서 이만큼
벌어진다.

### 이 실험이 검증하는 것과 검증하지 못하는 것

- 검증됨: 파서(표준 FJS 포맷) -> 재사용 디코더(`VAA_decode`) -> GA 파이프라인이 우리 실제 목표 스케일
  데이터(10job/5machine/196공정/2AGV)에서 크래시 없이 끝까지 돌아 유한한 Cmax를 낸다.
- 검증 안 됨(설계상 애초에 불가능): SPT 기계선택 자체가 문헌 수준 성능을 낼 거라는 보장은 없음 -
  이건 baseline일 뿐, 우리 프로젝트가 LLM으로 개선하려는 대상이다.
- 확인 못함: 격차(82%)에서 (1) 기계선택 규칙 품질 vs (2) GA 크로스오버 버그로 인한 탐색 부족, 각각의
  기여분을 분리하지 않았음. 필요하면 크로스오버를 고쳐서(POX 반환값만 수정) 같은 SPT 규칙으로 재실행하면
  분리 가능.
