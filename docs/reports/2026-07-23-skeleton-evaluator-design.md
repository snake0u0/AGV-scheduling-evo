# 보고서 - B안 skeleton / evaluator 설계

작성 2026-07-23. 대상: STATUS.md "지금 뭘 하면 되나" 1~4번(파서 3종 / evaluator / replay 검증 / LLM 교체 인터페이스).
이 문서는 **구현 전 설계**이며, 설계 근거가 되는 규약은 전부 오늘 데이터로 직접 검증했다(추측 아님).

## 결론 (한눈에)

- **핵심 구조 = "타이밍 코어 1개 + 프론트엔드 2개"**. 공개 해를 재생하는 `replay`와 GA가 쓰는 `decode`가
  **동일한 시간 계산 코어**를 공유한다. replay가 문헌 Cmax를 정확히 재현하면, 그 검증이 GA 결과에도
  그대로 상속된다.
- **오늘 검증으로 규약 3개를 확정**했고, 그 중 하나는 **이전 세션 결론을 뒤집는 정정**이다(아래 §1).
- **LLM이 진화시킬 자리 = AGV 선택 규칙**. Han 2024의 Decoding1/Decoding2를 **같은 인터페이스로 표현
  가능**하게 설계했으므로, 두 baseline이 자동으로 정확한 ablation이 된다.
- **착수 순서 확정**: Dauzere 계보(travel matrix 확보됨)로 replay 검증 먼저 -> 통과 후 GA -> 그 다음 LLM.
  DeroussiNorre(fjsp1 -> 134)는 **travel matrix 미확보로 지금 착수 불가**(아래 §9, 오늘 확정).

## 1. 오늘 데이터로 확정한 규약 (설계의 전제)

### (a) [정정] 같은 기계로 이어지는 연속 공정에는 운반이 없다

**이전 세션에서 "예외 없이 항상 AGV를 배정한다"고 결론냈던 것은 틀렸다. 정정한다.**
Han 2024 MILP 원문(제약식 (1) `Σ X_ijkv = 1`)만 보면 항상 배정이 맞지만, **우리가 실제로 쓸 벤치마크
데이터(Berterottière 해 파일)는 반대 규약**을 쓴다. 공개 해 파일에서 운반 작업 수가 공정 수보다 적은 것을
발견하고, 누락된 운반이 정확히 어떤 경우인지 3개 인스턴스에서 전수 대조했다:

| 인스턴스 | 공정 수 | 운반 수 | 누락 | "직전 공정과 같은 기계"로 설명되는 비율 | 역방향 위반 |
|---|---|---|---|---|---|
| 01a (2veh) | 196 | 151 | 45 | **45/45** | 0 |
| 07a (2veh) | 293 | 258 | 35 | **35/35** | 0 |
| 13a (6veh) | 387 | 345 | 42 | **42/42** | 0 |

양방향 완전 일치(누락된 것은 전부 같은 기계 케이스이고, 존재하는 운반 중 같은 기계 케이스는 0개).
**규약 확정: 직전 공정과 같은 기계면 운반 작업을 만들지 않는다.** 이 경우 차량은 전혀 관여하지 않고,
작업물은 기계에 그대로 머문다.

부수 효과: 어제 후보에서 제외했던 `fyqiqi`의 `eta` 변수(같은 기계면 운반 생략)는 **개념 자체는 이 벤치마크
규약과 맞았다**. 저자가 "정의 오류"로 표시한 것은 아마 개념이 아니라 그 식이 비선형(`x*x`)이라 MILP에서
그대로 못 쓰는 문제였을 가능성이 크다. 다만 그 코드를 쓸 이유는 여전히 없다(가공시간 x3 등 다른 변형이 있음).

주의: DeroussiNorre 계보에서는 이 케이스가 **아예 발생하지 않는다**(기계가 (1,2)(3,4)(5,6)(7,8) 쌍으로
묶여 있고 연속 공정이 항상 다른 쌍에 속함 -> 공정 19개, 운반 19개로 정확히 일치). 즉 fjsp1-10 replay에서는
이 규약이 결과에 영향을 주지 않고, Dauzere 계보에서만 결정적으로 중요하다.

### (b) 전역 공정 번호 = job 순서대로 1부터 연속

해 파일의 `M*` 줄에 적힌 번호가 무엇인지 확인했다. job 1의 공정들이 1,2,3, job 2가 4,5,6... 식으로
연속 부여된다는 가설로 전 인스턴스를 검사한 결과 **기계 적격성 위반 0건**(어떤 공정도 처리 불가능한
기계에 배정되지 않음). 4개 인스턴스에서 확인. 이 번호 체계를 내부 canonical id로 그대로 채택한다.

### (c) 해 파일은 4개 하위문제를 전부 결정한다

`M<k>` 줄 = 기계 k가 처리한 공정 순서 -> **기계 배정 + 기계 순서** 결정.
`V<v>` 줄 = 차량 v가 수행한 운반 순서 -> **AGV 배정 + AGV 순서** 결정.
따라서 replay에는 어떤 정책도 개입하지 않으며, **시간 계산 로직만 순수하게 검증**된다.
(모든 인스턴스에서 `#M줄 == 기계 수`, `M줄 안의 공정 총합 == 전체 공정 수` 확인 완료.)

### (d) 헤더 3번째 필드는 신뢰하지 않는다

`DeroussiNorre/fjsp*.txt`의 헤더 3번째 값이 전부 2인데, **차량 수(2)와 공정당 대체기계 수(2)가 우연히
같아서** 어느 쪽인지 구분되지 않는다. 반면 `Dauzere_Data/`는 헤더 3번째가 1인데 실제로는 2/4/6대로 실험된다
(차량 수는 해 파일 쪽에 있음). **결론: 3번째 필드는 파서에서 읽되 절대 사용하지 않는다.** 차량 수는
실험 설정 또는 해 파일 헤더에서만 가져온다.

## 2. 모듈 구조

A안 자산(`sim/`, `ahd/`)은 STATUS.md 방침대로 **건드리지 않는다**. B안은 새 패키지로 분리한다.

```
fjspt/
  instance.py    # Instance 데이터 모델 + 파서 3종 + 데이터셋 레지스트리
  solution.py    # Solution(완전지정 해) / Chromosome(OS,MS) 표현
  timing.py      # ★ 타이밍 코어 (유일한 시간 계산 지점)
  evaluator.py   # decode: (OS, MS, rule) -> Solution + Cmax   [GA용 프론트엔드]
  replay.py      # replay: 공개 해 파일 -> Cmax + 규약 탐색     [검증용 프론트엔드]
  rules.py       # AGV 선택 규칙: Decoding1/2 등 baseline + 진화된 규칙 컴파일
  ga.py          # GA 뼈대 (DCGA 구조 준수)
  experiment.py  # train/test 분할, 반복 실행, 통계, 결과표 생성
```

`ahd/llm.py`(ClaudeCliLLM)는 **그대로 재사용**한다. 이미 tool-contamination이 수정된(commit `3a8ad01`)
검증된 LLM 호출 계층이고, B안에서도 하는 일(텍스트로 규칙 제안받기)이 동일하다.

## 3. 데이터 모델

```python
Instance:
    name: str                     # "01a", "fjsp1"
    n_jobs: int
    n_machines: int
    jobs: list[list[list[tuple[int, int]]]]   # jobs[j][o] = [(기계, 처리시간), ...]
    travel: list[list[int]]       # (m+1)x(m+1), 인덱스 0 = L/U, 행=출발 열=도착, 비대칭
    n_vehicles: int               # 인스턴스 파일이 아니라 실험 설정에서 주입
    source: dict                  # 출처(파일 경로, 포맷, travel matrix 출처) - 논문 재현성용
```

**인덱싱 규약(버그 예방)**: 기계는 파일과 동일하게 **1..m**로 유지하고 **0은 L/U**로 예약한다.
이렇게 하면 `travel[a][b]`를 그대로 쓸 수 있고, 0-index 변환에서 생기는 오프바이원을 원천 차단한다.
(오늘 Aihong-Sun 코드 테스트에서 실제로 겪은 종류의 버그다.)

```python
Solution:                          # 완전 지정된 해 (replay 입력 / decode 출력)
    machine_of:  dict[gid, int]        # 공정 -> 기계
    machine_seq: dict[int, list[gid]]  # 기계 -> 공정 순서
    vehicle_of:  dict[gid, int]        # 운반이 있는 공정만
    vehicle_seq: dict[int, list[gid]]  # 차량 -> 운반 순서

Chromosome:                        # GA 개체
    OS: list[int]                  # job id 반복 순열, 길이 = 전체 공정 수
    MS: list[int]                  # 각 공정의 적격기계 집합 내 인덱스, canonical 공정 순
```

`Solution`은 공개 해 파일의 구조와 1:1 대응한다(§1c). 즉 **파일을 읽으면 바로 Solution이 되고,
decode도 Solution을 만든다.** 두 경로가 같은 타입으로 수렴하는 것이 이 설계의 핵심이다.

## 4. 파서 3종

공통 인터페이스 `parse(path) -> Instance`. 포맷별로 앞부분만 다르고 결과 타입은 동일하다.

| 포맷 | 대상 | 헤더 | 공정 표현 | 주의 |
|---|---|---|---|---|
| A. Bilge-Ulusoy 계보 | `DeroussiNorre/` | `nJob nMachine ?` | `대체기계수 m1..mk 공통시간` | 대체기계들의 **처리시간이 하나로 공유됨**(다른 포맷과 다름) |
| B. 표준 FJS | `Dauzere_Data/`, `Homayouni_Brandimarte/` | `nJob nMachine ?` | `적격기계수 (기계,시간)...` | 가장 흔한 형태 |
| C. Fattahi | `fattahi/` | `총공정수 선행관계수 기계수` | 선행쌍 리스트 -> 공정별 `(적격기계수 (기계,시간)...)` | **job 경계가 명시되지 않음**. 선행쌍으로 체인을 복원해야 함. job 수 = 총공정수 - 선행관계수 (sfjs01: 15 - 10 = 5 job 확인) |

- 3개 포맷 모두 헤더 3번째 필드는 읽되 **사용 금지**(§1d).
- 파서는 `travel`을 채우지 않는다. travel matrix는 **별도 파일에서 오고 인스턴스와 짝지어야 하므로**
  데이터셋 레지스트리가 담당한다(§9의 리스크와 직결).

## 5. Evaluator 설계 (핵심)

### 5.1 타이밍 코어 (`timing.py`)

**유일한 시간 계산 지점.** 입력은 완전 지정된 `Solution`, 출력은 각 공정의 시작/종료 시각과 Cmax.
아래 점화식을 위상 순서로 전파해서 푼다.

공정 `o`(job j의 i번째)에 대해:

```
운반 필요 여부:
    i == 0                        -> 필요 (L/U에서 출발)
    machine(prev) != machine(o)   -> 필요
    machine(prev) == machine(o)   -> 불필요           # §1a 확정 규약

운반이 필요한 경우 (차량 v = vehicle_of[o]):
    pick_loc = 0 if i == 0 else machine(prev)          # 0 = L/U
    ready    = 0 if i == 0 else C[prev]                # 작업물이 준비되는 시각
    (v_free, v_loc) = v의 직전 운반 완료시각/위치       # 없으면 (0, 0) = 시각 0에 L/U
    pickup   = max(v_free + travel[v_loc][pick_loc], ready)   # 공차 이동 후 대기 가능
    arrive   = pickup + travel[pick_loc][machine(o)]          # 적재 이동
운반이 불필요한 경우:
    arrive   = C[prev]                                  # 기계에 그대로 머무름

기계 제약:
    S[o] = max(arrive, C[기계에서의 직전 공정])
    C[o] = S[o] + 처리시간(o, machine(o))

Cmax = max C[o]
```

- `pickup = max(v_free + 공차이동, ready)` 형태가 핵심이다. 차량이 먼저 도착하면 대기하고, 작업물이
  먼저 준비되면 차량을 기다린다. **이 식은 오늘 Kumar 2011 E11 인스턴스에서 문헌 최적값 96을 정확히
  재현하는 것으로 검증된 형태**다(Aihong-Sun `VAA_decode`와 동일 의미).
- 모든 차량은 **시각 0에 L/U(인덱스 0)에서 출발**. 마지막 공정 후 **L/U 복귀 없음**
  (Berterottière 2025 §3.1 원문에 명시된 가정, 오늘 확인).
- 적재/하역 시간은 **0으로 가정**. 근거가 없는 가정이므로 replay가 틀리면 여기부터 의심한다(§6.2).
- 순서 지정이 모순되면(사이클) 검출해서 예외를 던진다. 조용히 잘못된 값을 내지 않게 한다.

### 5.2 decode 프론트엔드 (`evaluator.py`)

`decode(instance, OS, MS, rule) -> (Solution, Cmax)`

```
1. MS로 각 공정의 기계를 결정
2. OS를 훑으며 (job의 k번째 등장 = 그 job의 k번째 공정) 순서대로 처리
3. 각 공정에 대해:
     운반 불필요면 -> 차량 개입 없이 시간만 계산
     운반 필요하면 -> 후보 차량들의 특징을 계산해 rule로 하나 선택
4. 선택 결과를 Solution에 기록하면서 시간 전파
```

**자기검증 장치**: `decode`가 만든 `Solution`을 다시 `timing.simulate`에 넣으면 **같은 Cmax가 나와야
한다.** 두 경로(증분 구성 vs 일괄 전파)가 일치하는지 테스트로 상시 확인한다. 공짜로 얻는 강한 회귀 테스트다.

## 6. Replay 검증 설계 (`replay.py`)

### 6.1 기본 동작

공개 해 파일 -> `Solution` -> `timing.simulate` -> Cmax 를 헤더의 Cmax와 대조.
정책이 전혀 개입하지 않으므로 **시간 계산 로직만** 검증된다. 산출물은 논문에 그대로 넣을 표다:

| 인스턴스 | 차량 | 문헌 Cmax | 우리 replay Cmax | 일치 |
|---|---|---|---|---|
| 01a | 2 | 2752 | ? | ? |
| ... | | | | |

**성공 기준**: Dauzere 계보 18인스턴스 x 2/4/6대 = 54케이스 전부 정확히 일치.

### 6.2 규약 탐색 모드 (replay를 진단 도구로 쓰기)

replay가 틀리면 "어디가 틀렸는지" 모르는 채로 끝나면 안 된다. 문헌이 명시하지 않아 우리가 **가정한
항목이 소수(3개)**이므로, 이들의 조합을 전수 시도해서 어느 조합이 문헌값을 재현하는지 찾는 모드를 둔다.

| 미확정 가정 | 후보 |
|---|---|
| 적재/하역 시간 | 0 / 상수 c |
| 차량 초기 위치 | 전부 L/U / 첫 작업 위치 |
| 공차 이동 중 재배차 | 불가(가정) / 가능 |

조합 수가 작으므로 완전 탐색이 가능하다. 어느 조합이 54케이스를 전부 맞히면 그 조합이 문헌의 실제
규약이고, **그 사실 자체가 논문에 쓸 수 있는 발견**이 된다(원문에 안 적힌 걸 데이터로 역추론).

## 7. GA 뼈대 (`ga.py`)

DCGA(Han 2024)와 **같은 인코딩/연산자**를 쓴다. 비교의 공정성이 목적이므로 여기서 창의성을 발휘하지 않는다.

| 구성요소 | 채택 | 근거 |
|---|---|---|
| 인코딩 | OS(job 반복 순열) + MS(적격집합 인덱스) | Han 2024 §4.2 |
| 초기화 | 무작위 | Han 2024 §4.1 |
| 선택 | 이진 토너먼트 + 엘리트 보존 | Han 2024 §4.4 |
| 교차 | OS: POX / MS: 균등교차 | Han 2024 §4.5 |
| 변이 | OS: swap·insert·inversion / MS: 재배정 | Han 2024 §4.6 |
| 적합도 | `decode(...)`의 Cmax (최소화) | - |
| 종료 | 세대 수 또는 시간 예산 | 문헌 비교시 시간 기준 필요 |

주의: 어제 테스트한 Aihong-Sun 저장소의 POX는 **계산 결과를 버리고 원본을 반환하는 죽은 코드**였다.
우리 구현에서는 POX 단위 테스트(자식이 부모와 다르고, job별 공정 수가 보존되는지)를 반드시 넣는다.

## 8. LLM이 진화시키는 자리 (`rules.py`)

### 8.1 인터페이스

A안에서 이미 쓰던 `policy(features) -> score` 형태를 **그대로 유지**한다(`sim/rule.py`의 제한된 eval
컴파일 방식 재사용 가능). 디스패처는 최고 점수 후보를 고른다.

운반 작업 t를 처리할 때, 각 후보 차량 v에 대해 제공하는 특징:

| 특징 | 의미 |
|---|---|
| `empty_travel` | 차량 현재 위치 -> 픽업 지점 (공차) |
| `loaded_travel` | 픽업 지점 -> 목적 기계 (적재) |
| `arrival` | 이 차량을 쓸 때의 도착 시각 (Decoding1이 쓰는 값) |
| `wait` | 차량이 작업물을 기다리며 노는 시간 |
| `agv_free` | 차량이 비는 시각 |
| `agv_cum_travel` | 차량 누적 이동시간 (Decoding2가 쓰는 값) |
| `machine_free` | 목적 기계가 비는 시각 |
| `remaining_ops` | 해당 job의 남은 공정 수 |

### 8.2 baseline이 같은 인터페이스로 표현된다 (설계의 핵심)

- **Decoding1** (가장 이른 도착, 동점이면 고정 차량) = `-arrival`
- **Decoding2** (가장 이른 도착, 동점이면 누적이동 최소) = `-arrival - eps * agv_cum_travel`

즉 문헌의 두 디코딩이 **우리 규칙 공간의 두 점**이 된다. 따라서 LLM이 찾은 규칙과의 비교가
"다른 알고리즘과의 비교"가 아니라 **같은 공간 안의 ablation**이 되어 훨씬 방어하기 쉽다.
Han 2024가 "둘 중 어느 것도 항상 우월하지 않다"고 스스로 인정한 지점이 정확히 우리 진입점이다.

### 8.3 확장 여지 (지금은 하지 않음)

STATUS.md는 "AGV 배정 + 순서 **동시** 진화"를 말한다. 위 설계는 OS가 순서를 고정하므로 배정만 진화한다.
순서까지 진화시키려면 "준비된 운반 작업 풀에서 (차량, 작업) 쌍을 고르는" 이벤트 구동 디스패치로 바꿔야
하는데, 그러면 DCGA와의 직접 비교가 깨진다.

**권고: 1단계는 배정만(DCGA 직접 비교 가능), 2단계에서 순서까지 확장.** 다만 규칙 시그니처를 처음부터
"후보 (차량, 작업) 쌍들의 목록을 받아 하나를 고른다"로 두면, 1단계에서는 작업이 항상 1개인 특수 경우가
되어 **인터페이스 변경 없이** 2단계로 넘어갈 수 있다. 이렇게 설계한다.

## 9. 실험 설계

### 9.1 데이터 분할 (신뢰성의 핵심)

LLM이 규칙을 진화시킬 때 쓰는 인스턴스와 결과를 보고하는 인스턴스를 **반드시 분리**한다.
분리하지 않으면 "그 인스턴스에 과적합된 규칙"이라는 지적을 방어할 수 없다.

- **train**: Dauzere 소수(예: 01a, 07a, 13a - 5/8/10 기계를 하나씩)
- **test**: 나머지 15개 x 2/4/6대. 진화 과정에서 한 번도 보지 않음.

### 9.2 비교 대상

| 코드 | 내용 |
|---|---|
| B1 | Decoding1 + 같은 GA |
| B2 | Decoding2 + 같은 GA |
| B3 | 무작위 규칙 + 같은 GA (규칙이 실제로 기여하는지 확인용 하한) |
| P | LLM 진화 규칙 + 같은 GA |
| 문헌 | Berterottière 2024 tabu search (해 파일 헤더의 Cmax, 600초) |

GA 하이퍼파라미터와 시간 예산은 B1/B2/B3/P가 **완전히 동일**해야 한다. 차이는 규칙 하나뿐이어야 한다.

### 9.3 지표

Cmax, 문헌 best-known 대비 gap(%), 실행시간. GA가 확률적이므로 **시드 고정 + 다회 반복(최소 10회) 후
평균/최소/표준편차**를 보고한다.

### 9.4 계산 예산 추정

어제 실측: 196공정 인스턴스에서 decode 1회 약 0.4ms, GA(pop 100 x gen 100) 약 4초.
규칙 1개 평가 = train 3인스턴스 x 4초 = 약 12초. LLM 세대당 20개 규칙 x 10세대 = 200규칙 = 약 40분.
**충분히 감당 가능**하다.

## 11. 착수 순서 (각 단계의 통과 기준)

```
1. instance.py (파서 3종 + 레지스트리)
   -> 검증: 전 인스턴스 파싱 성공 + 공정 수가 해 파일의 M줄 총합과 일치 (오늘 검증 스크립트 재사용)
2. timing.py + replay.py
   -> 검증: Dauzere 54케이스 replay Cmax == 문헌 Cmax (틀리면 §6.2 규약 탐색)
3. evaluator.py (decode)
   -> 검증: decode 결과를 simulate에 재투입시 Cmax 동일 (자기검증)
4. rules.py (Decoding1/2) + ga.py
   -> 검증: B1/B2가 문헌 Cmax 대비 합리적 범위. POX 단위 테스트 통과
5. LLM 루프 연결 (ahd/llm.py 재사용)
   -> 검증: P가 train에서 B1/B2 초과, test에서도 유지되는지
```

**2번이 이 프로젝트 전체의 관문이다.** 여기서 문헌값이 재현되지 않으면 그 위의 어떤 결과도 신뢰할 수 없고,
반대로 통과하면 그 검증이 3~5번 전부에 상속된다.
