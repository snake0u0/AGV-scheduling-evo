# solution.py 파악

> 정리: 답이 다 채워진 파일을 파싱하는 파일

- 솔루션 설명: 어떤 machine/vehicle이 어떤 operation을 담당하고, 어떤 순서로 operation들을 처리할지에 대해서.
- replay.py, evaluator.py가 프론트 엔드 담당..?
    replay.py: 
    evaluator.py: 
- solution 클래스

## 해결된 의문사항들

1. 주석에서 replay.py랑 evaluator.py 두개가 프론트엔드를 담당한다것의 의미: 서로 다른 입구로 들어와도 결국 같은 내부형태로 합쳐지고, 그 내부 형태가 같은 핵심 엔진에 먹혀 들어간다는 의미.
    published 텍스트 파일: replay.py,
    ga 염색체 + 규칙:  evaluator.py, 
    replay.py, evaluator.py → 이 파일의 Solution class를 통해서 timing.py(헥심 엔진)

2. replay.py: 우리 population이 아닌 문헌에 공표된 해 파일 딱 하나를 읽어서, 우리 타이밍 코어가 그 논문이 주장하는 Cmax와 같은 값을 내는지 검증하는 도구
    evaluator.py: GA개체 하나를 실제로 시뮬레이션해서 완전한 스케줄로 바꾸는 함수.

3. Solution 클래스에서 
    machine_of: gid → machine, 공정 하나가 어느 기계에서 처리되나
    machine_seq: machine → [gid], 그 기계가 어떤 순서로 처리되나
    vehicle_of: gid → vehicle, 공정 하나를 어느 AGV가 운반하나
    vehicle_seq: vehicle → [gid], 그 AGV가 어떤 순서로 운반하나
    meta: 위 4개 밖의 잡다한 정보(출처, 문헌 Cmax 등)

4. parse_solution_file(path): 남(문헌 저자)이 이미 써놓은 텍스트 파일(예: dpp01a_2veh.txt)을 읽어서, 우리 파이썬 객체(Solution)로 바꾸는 것.  timing.py에 넣어 우리 계산이 그 파일의 published_cmax와 일치하는지 검증하는 데 사용(=replay.py가 하는 일)

5. solution.py 이 파일은 문헌에서 확정된 스케줄 하나가 어떤 모양인지"를 정의하는 데이터클래스 하나, 그리고 "문헌 파일 하나를 읽어서 그 모양으로 바꾸는" 함수 하나. 그게 전부. Solution 모양을 채우는 두 가지 다른 방법(문헌 파일 읽기 vs GA 개체 디코딩)이 있을 뿐, population이나 LLM 자체에 대한 지식은 이 파일에 없다.
